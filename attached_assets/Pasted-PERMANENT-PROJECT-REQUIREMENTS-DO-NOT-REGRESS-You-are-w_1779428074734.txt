1. ATT (App Tracking Transparency) Prompt Timing — CRITICAL
────────────────────────────────────────────────────────────────────

The ATT prompt MUST be shown BEFORE any ad or tracking request fires.
If ATT runs after the first ad request, the SDK locks into 
non-personalized ads for the entire session — even for users who 
would have granted consent. This silently destroys ad revenue and is 
not recoverable without an app restart.

Required ordering in MainApp.tsx (enforce strictly, top-to-bottom):

  1. gatherConsent()              — UMP / GDPR consent gathered first
  2. ATT prompt                   — requestTrackingPermissionsAsync()
                                    awaited to completion
  3. mobileAds().initialize()     — only after ATT resolves
  4. <AdBanner /> mounts          — only after initialize resolves

Rules:
- Do NOT mount any ad component, call mobileAds(), or fire any 
  tracking/analytics SDK init before ATT resolves.
- Do NOT fire ATT in parallel with ad init — it must be awaited.
- Do NOT move ATT into a child component, useEffect without ordering 
  guarantees, or any code path that can race with ad mounting.
- If you add a new ad surface, analytics SDK, or tracking library, 
  it must be gated behind the same post-ATT barrier.

Verification checklist before shipping:
[ ] MainApp.tsx shows the four steps in the exact order above
[ ] No mobileAds(), no ad component, and no tracking SDK appears 
    anywhere upstream of the ATT await
[ ] Cold-start on a fresh iOS install shows the ATT dialog before 
    any ad ever appears on screen
