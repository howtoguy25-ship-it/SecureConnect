PART A — END-TO-END ENCRYPTION (REAL, NOT COSMETIC)
═══════════════════════════════════════════════════════════════

Implement true E2EE across CHAT, STATUS, LOCKER, and CALLS
using an established protocol. Requirements:

1. PROTOCOL
  • Use Signal Protocol (libsignal) for chat + status
  • Use SRTP + DTLS-SRTP with E2EE key exchange for calls
  • Use per-user master key derived via Argon2id from a
    passphrase + server-stored salt for locker
  • NO custom crypto. NO rolling your own primitives.

2. KEY MANAGEMENT (SERVER-SIDE INFRASTRUCTURE)
  • Build a Key Distribution Server with these tables:
      - identity_keys (userId, publicKey, createdAt)
      - signed_prekeys (userId, keyId, publicKey, signature,
        createdAt, expiresAt)
      - one_time_prekeys (userId, keyId, publicKey, used)
      - device_keys (userId, deviceId, registrationId)
  • Server stores ONLY public keys. Private keys never leave
    the device.
  • Endpoints:
      POST /api/keys/register
      GET  /api/keys/bundle/:userId
      POST /api/keys/replenish-prekeys
      DELETE /api/keys/:deviceId
  • Rotate signed prekeys every 7 days. Auto-replenish
    one-time prekeys when count drops below 10.

3. CLIENT-SIDE KEYSTORE
  • Store private keys in iOS Keychain / Android Keystore
    (hardware-backed where available)
  • Use expo-secure-store with requireAuthentication: true
  • Never log, export, or transmit private keys

4. VERIFICATION
  • Show safety numbers / key fingerprints in chat info
  • Warn on key change ("Security code changed")
  • Optional QR scan for out-of-band verification

PART B — LOCKER: COMPLETE REBUILD
═══════════════════════════════════════════════════════════════

Current state is broken. Rebuild as follows:

1. ENCRYPTION AT REST
  • Derive locker key: Argon2id(PIN + serverSalt + userSalt)
    — params: memory=64MB, iterations=3, parallelism=4
  • Encrypt every item client-side with AES-256-GCM before
    upload (unique IV per item)
  • Server stores ONLY ciphertext + IV + auth tag. Never the
    PIN, never the derived key, never plaintext.
  • DB schema change:
      hidden_locker_items:
        - ciphertext (bytea)
        - iv (bytea)
        - auth_tag (bytea)
        - encrypted_media_key (bytea)  ← for media items
      REMOVE: content (text), media_url (plain)
  • Media files in GCS: encrypt blob client-side, upload
    ciphertext only. Signed URL grants access to ciphertext;
    decryption key never touches server.

2. BIOMETRIC UNLOCK
  • Integrate expo-local-authentication
  • Flow: biometric prompt → unlocks Keychain-stored locker
    key → decrypts items
  • Fallback to PIN if biometric fails or is disabled

3. FAILED-ATTEMPT LOCKOUT
  • Add columns: locker_failed_attempts (int),
    locker_locked_until (timestamp)
  • Policy: 5 wrong PINs → 1 min lockout
           10 wrong → 15 min
           15 wrong → 1 hour
           20 wrong → wipe locker (with prior warning at 15)
  • Rate-limit /api/locker/verify-pin server-side: max 5
    attempts per 15 min per userId + IP
  • Reset counter on successful unlock

4. PIN STRENGTH + RECOVERY WARNING
  • Require minimum 6-digit PIN (allow alphanumeric option)
  • At creation, display modal:
    "If you forget your PIN, your locker contents CANNOT be
    recovered. Anthropic-style E2EE means we cannot help.
    Write your PIN somewhere safe or set up a recovery
    phrase below." [Confirm] [Set Recovery Phrase]
  • Optional BIP-39 12-word recovery phrase encrypted by the
    same locker key (stored encrypted on device only)

5. SIGNED URL HARDENING
  • Signed URLs expire in 60 seconds (not hours)
  • URLs require bearer token + userId match server-side
    before signing
  • Add /api/locker/media/:itemId endpoint that re-signs on
    each request after auth check
  • Never store the signed URL in DB — generate on demand

6. SCREENSHOT BLOCKING
  • Add expo-screen-capture
  • In HiddenLockerScreen.tsx and locker item viewer:
      useEffect(() => {
        preventScreenCaptureAsync();
        return () => allowScreenCaptureAsync();
      }, []);
  • On Android, set FLAG_SECURE on the activity
  • Detect screenshot attempts and log to audit table
