1. ATT + UMP + Ad Init Ordering — CRITICAL
────────────────────────────────────────────────────────────────────

The correct startup order for ads on iOS is:

  ATT  →  UMP (gatherConsent)  →  mobileAds().initialize()  →  ads

ATT MUST run FIRST so that UMP reads the resolved IDFA state when
making consent decisions. Running UMP before ATT causes UMP to gather
consent against an unresolved IDFA, then ATT changes the state 
underneath it, producing mismatched signals and degraded ad 
personalization. This also matches Google's current AdMob sample 
code.

Required ordering in client/MainApp.tsx (enforce strictly, 
top-to-bottom, each step awaited to completion before the next):

  1. ATT prompt              — requestTrackingPermissionsAsync()
                               awaited to completion
  2. gatherConsent()         — UMP / GDPR consent gathered after ATT
                               has resolved the IDFA state
  3. mobileAds().initialize()— only after both ATT and UMP resolve
  4. <AdBanner /> mounts     — only after initialize resolves

Safety invariant (must always hold):
  Nothing ad-related fires before ATT has resolved. No ad component, 
  no mobileAds() call, no tracking/analytics SDK init may execute 
  upstream of the ATT await.

Rules:
- Do NOT reorder to UMP → ATT → init. UMP must see the post-ATT
  IDFA state.
- Do NOT fire ATT, UMP, and init in parallel — each must be awaited
  in sequence.
- Do NOT move ATT, UMP, or init into a child component, useEffect
  without ordering guarantees, or any code path that can race with
  ad mounting.
- If you add a new ad surface, analytics SDK, or tracking library,
  it must be gated behind the same post-ATT, post-UMP, post-init
  barrier.
- If the doc (replit.md or similar) and code ever disagree on this
  ordering, the CODE order above (ATT → UMP → init) is the source 
  of truth — update the doc to match, not the other way around.

Verification checklist before shipping:
[ ] client/MainApp.tsx shows the four steps in the exact order above
[ ] Each step is awaited; none run in parallel
[ ] No mobileAds(), no ad component, and no tracking SDK appears
    anywhere upstream of the ATT await
[ ] Cold-start on a fresh iOS install shows the ATT dialog FIRST,
    then the UMP consent form (if applicable), then ads load
[ ] replit.md (or whichever doc describes this flow) reflects
    ATT → UMP → init, not the reverse
