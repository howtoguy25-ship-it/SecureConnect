GAP 1 — LOCKER: CLOSE THE PLAINTEXT GAP (HIGHEST PRIORITY)
═══════════════════════════════════════════════════════════════

CURRENT STATE: PIN gates the API. Database stores content
in cleartext. GCS stores media at plain signed URLs. Anyone
with DB or bucket access reads everything. This contradicts
the security claim shown to users.

REQUIRED IMPLEMENTATION:

a) KEY DERIVATION (CLIENT ONLY)
  • locker_master_key = Argon2id(
        passphrase = user PIN/passphrase,
        salt       = per-user 32-byte salt (generated once,
                     stored in iOS Keychain / Android
                     Keystore — NEVER server-side),
        memory     = 64 MiB,
        iterations = 3,
        parallelism = 4,
        output     = 32 bytes)
  • Held in memory only while locker is unlocked. Wiped on
    lock, background, or screen-off.

b) HARDWARE-BACKED WRAPPING (FOR BIOMETRIC UNLOCK)
  • Generate non-exportable key in Secure Enclave (iOS) /
    StrongBox (Android), guarded by biometric.
  • Use it to wrap locker_master_key for biometric path.
  • PIN path re-derives via Argon2id each unlock.

c) PER-ITEM ENCRYPTION
  • For each locker item:
      data_key   = 32 random bytes (CSPRNG)
      iv         = 12 random bytes
      ciphertext = AES-256-GCM(data_key, iv, plaintext)
      wrap_iv    = 12 random bytes
      wrapped_dk = AES-256-GCM(locker_master_key, wrap_iv,
                               data_key)
  • Server row:
      hidden_locker_items(
        id, user_id, content_type,
        ciphertext      BYTEA,
        iv              BYTEA,
        auth_tag        BYTEA,
        wrapped_data_key BYTEA,
        wrap_iv         BYTEA,
        wrap_auth_tag   BYTEA,
        created_at)
  • DROP COLUMNS: content (text), media_url (plain).
    Migration: re-encrypt on next unlock; mark unmigrated
    rows and force user through migration flow.

d) MEDIA BLOBS
  • Encrypt blob client-side with its own data_key BEFORE
    upload.
  • Upload ciphertext to GCS in a private bucket. No
    public access, no long-lived URLs.
  • Signed URL valid 60 seconds, generated only after
    server-side auth check (userId match + valid session).
  • Never store the signed URL in DB. Endpoint
    GET /api/locker/media/:itemId re-signs on demand.

e) BRUTE-FORCE LOCKOUT
  • users table additions:
      locker_failed_attempts INT DEFAULT 0,
      locker_locked_until    TIMESTAMP NULL
  • Server endpoint /api/locker/verify-attempt:
      5 fails  → 1 min lock
      10 fails → 15 min lock
      15 fails → warning shown next unlock
      20 fails → wipe all hidden_locker_items rows
  • Rate limit per userId AND per source IP.
  • Reset counter on success.

f) SCREENSHOT BLOCKING
  • expo-screen-capture preventScreenCaptureAsync() on
    HiddenLockerScreen mount + item viewer mount.
  • Android FLAG_SECURE via config plugin so the OS
    blocks screenshots and recent-apps thumbnails.
  • Detected attempts → audit_log row.

g) RECOVERY POLICY
  • Default: no recovery. Forgotten PIN = lost data.
  • At PIN creation, modal:
    "If you forget this PIN, your locker cannot be
     recovered. The encryption keys live only on this
     device. Write the PIN somewhere safe, or set up an
     optional recovery phrase below."
  • Optional BIP-39 12-word phrase encrypted with the
    locker_master_key, stored locally only.

ACCEPTANCE TESTS (must all pass):
[ ] SELECT * FROM hidden_locker_items returns only
   ciphertext columns. No readable content.
[ ] Download a GCS blob directly — file is unreadable
   without the wrapped_data_key + locker_master_key.
[ ] Brute-force script against /api/locker/verify-attempt
   is blocked after 5 attempts.
[ ] Screenshot attempt on locker → black image (iOS) or
   blocked (Android).
[ ] Restore device backup to new phone → locker items
   cannot be decrypted without PIN (proves keys aren't
   in iCloud/Google backup).

GAP 3 — LOGOUT: CLEAR PUSH TOKEN
═══════════════════════════════════════════════════════════════

CURRENT STATE: Push token stays registered until next login
overwrites it. Low risk but residual.

REQUIRED:

a) On logout (client):
  • Call POST /api/push-token with body { pushToken: null }
  • Then revoke the FCM/APNs token locally via
    Notifications.unregisterForNotificationsAsync()
  • Clear any stored token in SecureStore.

b) Server endpoint:
  • Accept { pushToken: null } → set
    users.push_token = NULL, users.push_platform = NULL
  • Insert audit_log row: event = 'push_token_cleared'

c) Defensive cleanup on account deletion:
  • Same clearing happens, plus push_token row is also
    hard-deleted (not just nulled) in the device_tokens
    table if you maintain one.

ACCEPTANCE TESTS:
[ ] After logout, users.push_token IS NULL in DB.
[ ] Sending a test push to that user returns "no token".
[ ] Re-login overwrites with fresh token cleanly.
